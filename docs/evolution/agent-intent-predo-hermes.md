

在 **Hermes Agent** 系统中，用户发出的消息在到达 LLM 之前确实会经过一系列预处理和分析处理，但并非简单的"关键词过滤"，而是通过**多层次的中间件架构**和**上下文管理**进行处理。

## 预处理流程概览

根据 Hermes Agent 的架构设计，用户消息的流向大致如下：

```
用户输入
    ↓
┌───────────────────┐
│ 输入事件钩子 (Input Hook) │ ← 可拦截/修改消息
└───────────────────┘
    ↓
┌───────────────────┐
│ 内容扫描/安全检查 │ ← 危险命令审批、注入检测
└───────────────────┘
    ↓
┌───────────────────┐
│ 上下文组装 │ ← 注入记忆(Memory.md)、系统提示
└───────────────────┘
    ↓
┌───────────────────┐
│ 上下文压缩/优化 │ ← 5步结构化压缩，减少token
└───────────────────┘
    ↓
  LLM API 调用
```

## 具体的预处理机制

### 1. **输入事件预处理（Input Hook）**
Hermes 计划在扩展系统中增加 `input` 事件，用于用户消息的预处理 。这意味着在消息进入核心循环之前，可以通过钩子进行：
- 消息格式规范化
- 内容过滤或转换
- 注入前置信息（如上传文件扫描结果）

### 2. **内容扫描与安全检查**
- **危险命令审批**：在 `tools/approval.py` 中对特定工具调用进行审批拦截 
- **内容扫描**：`tools/memory_tool.py` 中进行输入验证 
- **Prompt 注入检测**：通过外部安全中间件（如 ShellWard）可进行 32 条注入规则检测（18 中文 + 14 英文）

### 3. **上下文组装与记忆注入**
在 `gateway/run.py` 和 `agent/prompt_builder.py` 中，系统会：
- 动态注入 **Memory.md**、**USER.md**、**SOUL.md** 等记忆文件 
- 添加系统提示层（System Prompt Layering）
- 注入 `[INTERNAL STATE]` 和行为指南（如情感稳态中间件）

### 4. **上下文压缩优化（5步结构化压缩）**
这是 Hermes 的核心创新之一。当上下文接近限制时，会触发 ：
1. **剪枝工具结果**（Prune tool results）
2. **头部保护**（Head protection）— 保留系统提示和关键记忆
3. **尾部保留**（Tail preservation）— 保留最近几轮对话
4. **中部摘要**（Middle summarization）— 对中间历史进行结构化摘要
5. **迭代精炼**（Iterative refinement）

### 5. **工具调用修复中间件**
在消息发往 LLM 前，系统会检查并修复"悬空"的工具调用（dangling tool calls）— 即 AI 消息中有 `tool_calls` 但没有对应 `ToolMessage` 响应的情况，自动注入合成错误消息以避免 API 报错 。

## 与简单"关键词处理"的区别

| 特征 | 传统关键词处理 | Hermes Agent 预处理 |
|------|-------------|-------------------|
| **机制** | 正则匹配/关键词替换 | 事件驱动钩子 + 中间件链 |
| **可扩展性** | 硬编码规则 | 可通过 Skills 和 Hooks 动态扩展 |
| **上下文感知** | 无 | 深度整合记忆系统和会话状态 |
| **安全层级** | 单层过滤 | 8层防御（通过外部中间件可达） |
| **Token 优化** | 无 | 多分辨率压缩，可减少 82% token  |

## 总结

Hermes Agent **没有采用简单的关键词提取或分析**，而是使用了一套**事件驱动的中间件架构**来处理用户输入。消息在进入 LLM 前会经过：输入钩子拦截 → 安全扫描 → 记忆/上下文组装 → 结构化压缩 → 工具调用完整性检查等多个环节。这种设计使得系统既保持了灵活性（可通过 Hooks 和 Skills 扩展），又能有效控制成本和保障安全。
